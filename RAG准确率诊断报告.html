核心结论

准确率低不是检索算法调参问题，而是四道关卡各自独立失效叠加的结果。按当前代码状态，一个典型的 MCU 问题在到达检索层之前就已大概率被拦截或降级。

更关键的是：你在 .env / settings.py 里改的所有检索参数（top_k、rrf_k、dense_weight、sparse_weight、context_max_chars、EMBEDDING_MODEL）在代码里全都没有被读取。这解释了为什么反复调参准确率没有变化——改动根本没有生效。

补充一条实测反直觉发现：稠密检索（BGE）在你这套数据上的 top1 正确率是 5/6，反超 BM25；而代码把稠密权重设成 1.0、稀疏设成 2.0～5.0 —— 把更准的那一路压到了 1/5。详见第 0 节实测。

关键推论：关卡 5 失败后，_llm_generate() 走"原文片段"降级路径（routes.py:318-326），把检索到的前 3 条 chunk 原文拼一拼就返回，文案还是"相关法律条文如下："。也就是说 —— 你当前看到的"答案"很可能根本不是 LLM 生成的，而是硬拼的原文片段。而这个降级结果还会被写进缓存保存 1 小时。

这两个是被精心调整过、并在注释里反复说明的优化，实际上一次都没跑起来。根因是入库侧把位置编号写进了 heading_number，而检索侧把它当语义标题用。

from sentence_transformers import CrossEncoder
# 中文可用 BAAI/bge-reranker-base 或 bce-reranker-base_v1

class BgeReranker:
    def rerank(self, query, hits, top_n=5):
        pairs = [(query, h.content) for h in hits]
        scores = self._model.predict(pairs)
        ranked = sorted(zip(scores, hits), key=lambda x: -x[0])
        return [Hit(..., rerank_score=float(s)) for s, h in ranked[:top_n]]

# 用法：RRF 先取 top_k*3 候选 → rerank → 取 top_k

7. 验证方法

修改前先建立基线，否则无法判断改动是否真的有效：

Step 1 · 建评测集

准备 30–50 条问题及标准答案（或至少标注"正确答案应出自哪个文档的哪个章节"）。务必先确定评测口径：
